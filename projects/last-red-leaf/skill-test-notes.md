# Paper Collage Skill 峰值测试记录

本文件记录《最后一片红叶》制作过程中发现的 Skill 问题与优化点。测试结束后统一讨论和实现；制作过程中只追加证据，不提前修改 Skill 行为。

## OPT-001：概念确认卡片应显式列出有界枚举参数

- 发现阶段：`capability-review` 的概念、预算与 provider 合并确认。
- 当前表现：卡片只询问“是否按当前故事、时长、画面方向、预算和服务方案继续？”，修改路径是一个笼统的“修改后再继续”自由文本入口。
- 用户问题：制作档位属于固定枚举，而且直接改变生图预算、分层深度、姿态数量、制作时间和成本；如果卡片不列出选项及数字，用户在确认前无法知道有哪些档位、各自是什么意思或如何选择。
- 期望行为：把 `draft`、`balanced`、`full-depth` 作为卡片中的直接可选项；针对当前幕数显示精确的生图尝试上限，并用一句话说明对最终成片的影响。
- 当前两幕示例：`draft` 最多 5 次，画面较扁平且大量复用；`balanced` 最多 6 次，关键场景有适量独立分层；`full-depth` 最多 9 次，最大化环境视差与角色姿态变化。
- 泛化原则：凡是固定枚举且会明显改变数字预算、输出范围或成本的参数，都应优先使用结构化选项，不应只藏在“其他/修改”自由文本中。
- 状态：已实现。`project:plan --json` 现在输出三个档位的精确预算、成片影响和时长权威；`project:confirm-concept` 要求结构化 `planDecision` 与当前计划完全一致。Skill 明确要求在首次确认和“修改后再继续”中直接列出这些选项。

## OPT-002：`project:assets-ready` 在 preview 阶段应支持幂等复核或提前失败

- 发现阶段：首轮预览因响度失败后，修改 `audio.narration.volume` 并重新执行就绪检查。
- 当前表现：命令先成功完成旁白同步、推断时长、字幕、v4 验证和 30/30 质量复核，最后才由 `project:advance` 报错“动作 assets-ready 不能在 preview 阶段执行”。
- 用户问题：输出看起来先全面成功再整体失败；在预览修订循环里，用户和 Agent 难以判断就绪复核是否有效、是否还需要补做步骤。
- 期望行为（二选一）：
  1. preview / human-review 阶段允许 `assets-ready` 作为幂等复核，只刷新同步与验证结果，不重复 advance；或
  2. 在执行任何写入和长检查前先识别阶段，快速返回“当前已在 preview，请直接运行 project:preview；如需完整复核请用某个明确命令”。
- 证据：响度修正后的 `project:validate` 为 0 错误 0 警告、`project:quality prepare` 为 30/30，但重复 `project:assets-ready` 仍以 exit 1 结束。
- 状态：已实现。命令在开始前读取阶段；`asset-production` 正常 advance，`preview` / `human-review` 执行幂等同步、音频预检、验证和质量复核并保持阶段不变，其他阶段快速失败。真实重入复验还确认：当新证据 hash 与旧人工审批不一致时，它会保持 `human-review` 不变、将受影响项重置为待审并安全阻止继续。

## OPT-003：在整段视频渲染前增加响度预检与音频-only 快速修订路径

- 发现阶段：第一次 784 帧预览完成后的最终报告。
- 当前表现：首轮画面、连续性、时长和真峰值全部通过，但综合响度为 -21.36 LUFS，低于 -16 ± 3 LUFS；将旁白总线从 1.0 调到 1.85 后，系统重新渲染全部 784 帧，第二轮得到 -16.01 LUFS。
- 用户问题：这是只影响音频混合的参数，但当前要重复完整浏览器逐帧渲染；full-depth 项目越长，等待成本越高。
- 期望行为：
  - 在 `assets-ready` 或 preview 前先根据旁白源文件、SFX 与配置做一次响度预检，给出推荐 gain；
  - 当视频画面指纹未变、仅音频总线变化时，复用无声视频流并重新混音/封装，再执行最终报告；
  - 仍由最终成片报告作为权威，不用预估替代真实验证。
- 证据：首轮 -21.36 LUFS / -8.71 dBTP；音量系数 1.85 后为 -16.01 LUFS / -3.15 dBTP，视觉质量指纹始终保持 30/30。
- 状态：已实现。新增 audio-only 时间线混音与 LUFS/真峰预检；本项目预检为 -15.98 LUFS / -3.17 dBTP，与完整成片报告 -16.01 / -3.15 基本一致。渲染缓存按视觉/音频指纹区分，只改音频时复用视频流重新混音封装，最终报告仍为权威。

## OPT-004：故事板节拍与 cue 证明点应在生产前形成可满足合同

- 发现阶段：`project:quality prepare` 的 composite gate。
- 当前表现：第二幕故事板有 5 个节拍，但批准的 proofTimes 只有 3 个；`s2-b1-leaf-lifts` 需要音效和可视动作，却没有自己的证明点。cue 不绑定 proof 会被质量门判为 needs-revision，而在 project.json 单独新增 cue proof 又会被验证器以“项目证明时刻必须与已批准故事板完全一致”拒绝。
- 本次绕行：把“掀叶”cue 延长到已有的“落叶成舟”证明点并绑定它，虽然合同可通过，但事件级证据不够精确。
- 期望行为：
  - 概念/故事板锁定前检查每个需要证明的节拍是否有 proofTime；
  - 或允许在不改变已批准叙事内容的前提下追加 cue-specific proof，并记录为证据增强而非概念变更；
  - 质量准备应在昂贵素材与整片渲染前报告这种不可满足合同。
- 状态：已实现。新故事板锁定为 schema v2，每个节拍显式声明 `proofTimeId` 或 null；带 `audioCue` 的节拍必须在锁定前绑定存在的事件级 proof，生产 cue 不得漂移到另一个 proof。v1 项目保持只读兼容。

## OPT-005：规划估算与执行时长的权威应进入机器确认合同

- 发现阶段：真实旁白同步后，约 28 秒规划估算收敛为 26.133 秒执行时间线。
- 当前表现：运行时已经区分用户明确时长和推断时长，但概念确认主要靠自然语言说明，容易把“约 28 秒”误读为必须补齐的目标。
- 期望行为：机器决策明确暴露 `human-target` 或 `content-derived`，并与档位、时长、幕数一起记录在概念批准中。
- 状态：已实现。`project:plan --json` 输出 `decision.durationAuthority`，`planDecision` 必须回填并匹配；推断时长继续以真实旁白、有限尾长和转场为执行权威。

## OPT-006：TTS 输出应在登记时做逐幕媒体时长预检

- 发现阶段：生产旁白生成和组装。
- 当前表现：旧流程只在 `project:sync` 时读取旁白时长；过长或过短的 TTS 可能到组装后才暴露。
- 期望行为：生产 voice request 声明逐幕允许时长，provider 结果一落盘就探测真实媒体并拒绝无法装入镜头的 take。
- 状态：已实现。voice request 新增可选 `timingBinding`；生产旁白由 Skill 强制使用，试听例外。`provider:record` / command adapter 登记前测量音频流、秒数和上下界，失败输出保留供诊断但不进入 manifest。

## OPT-007：组合证明和预览渲染应支持指纹级增量复用

- 发现阶段：full-depth 证明修订和响度二次预览。
- 当前表现：旧 `project:composition-proof` 会删除整个目录并重渲染所有 proof；任何预览修改也会重渲染全部帧。
- 期望行为：素材、构图、时间或画面配置未变时复用当前证据；只重做失效目标。预览区分视觉变化与音频-only 变化。
- 状态：已实现。proof report v2 保存逐帧/逐目标指纹和缓存统计，不再先清空目录；render cache 绑定视觉素材 hash、视觉配置、音频源 hash 和混音配置，缓存 artifact 还需匹配自身 SHA-256。

## OPT-008：质量门需要生成待填写的审核脚手架

- 发现阶段：30 项 full-depth asset/composite 质量复核。
- 当前表现：Agent 需要从 `quality-report.json` 手工构造数百行 `record-batch` JSON，容易漏检查、对象或证据路径。
- 期望行为：生成当前 pending 对象、required checks、pending checks 和可用证据的结构化草稿，但绝不自动判定通过。
- 状态：已实现。新增 `project:quality <slug> scaffold`；`passedChecks` / `failedChecks` 初始为空，必须检查证据、填写判断和说明后才能提交。

## OPT-009：风格批准后新增的耦合资产也需要统一证据包

- 发现阶段：第一幕素材在 style gate 后生产。
- 当前表现：style proof 有 alpha、棋盘格、紧裁和运动压力图；后续新增复杂抠图只有原图和组合裁切，证据标准不一致。
- 期望行为：所有 `supported-subject` / `registered-environment` 成员无论生成阶段都获得同一套可复核的拓扑证据。
- 状态：已实现。共享 `asset-evidence-lib` 被 style proof 与 composition proof 共同使用；post-style 成员证据写入 composition proof report 并自动进入质量脚手架建议路径。

## OPT-010：当前任务暴露的 Skill 版本与已安装缓存可能漂移

- 发现阶段：任务曾暴露 `0.8.0` Skill 路径，但插件登记和磁盘缓存已经是 `0.9.0`。
- 当前表现：正在运行的任务可能持有启动时的 Skill 清单快照；升级后旧目录消失，会出现悬空引用或误读旧流程。
- 期望行为：平台应让任务锁定并保留旧版本，或显式刷新到新版本；不能让会话目录、插件登记和缓存各自显示不同版本。
- 状态：仓库侧已缓解，平台根因未在本仓库内修复。Skill 现在禁止扫描“最高缓存版本”后静默继续，要求报告差异并新建任务；workspace doctor 比较 bootstrap marker 与 package 版本。Codex 会话 Skill 清单的热刷新/版本锁定仍需平台实现。

## OPT-011：响度分析器内部参数范围不应限制项目验收阈值

- 发现阶段：从真实 `0.10.0-dev.1` 插件缓存启动全新 starter 工作区并执行严格音频预检。
- 当前表现：starter 的项目合同要求 `-18 dBTP`，但 FFmpeg `loudnorm` 的分析目标参数只接受 `-9…0`；直接把项目阈值传入滤镜会在测量前失败。
- 期望行为：滤镜内部目标参数钳制到 FFmpeg 合法范围，测得的真实峰值仍按项目原始 `-18 dBTP` 合同判断，不能放宽成 `-9`。
- 状态：已实现并增加真实 FFmpeg 回归测试。安装缓存 starter 严格预检实测为 `-24.12 LUFS / -23.01 dBTP`，按原始 `-24 ± 3 / <= -18` 合同通过。

## OPT-012：已解析计划需要只读重显结构化决策

- 发现阶段：从安装缓存复验“修改后再继续”的档位菜单。
- 当前表现：旧 `project:plan --json` 只在首次写入计划时可用；恢复任务或已存在计划时，必须重新提供时长、幕数等写参数，无法安全地只读重显三档数字。
- 期望行为：写入模式继续要求完整规划参数；已解析计划只传 slug 与 `--json` 时，返回当前 `plan`、时长权威和三个档位准确预算，不改写项目或生产阶段。
- 状态：已实现并加入打包工作区集成测试。

## OPT-013：打包 starter 必须完整示范最新 proof 合同

- 发现阶段：最终安装缓存的首轮真实 Remotion 预览。
- 当前表现：starter 故事板已经是 v2 且节拍绑定 proof，但 `project.json` 的三个 cue 没有回填对应 `proofTimeId`，校验时出现逐项警告。
- 期望行为：内置样例不是只要“能渲染”，还必须是新项目可照抄的无警告最新合同示例。
- 状态：已实现。starter 的 establish、subject-arrives、lockup cue 分别绑定 `proof-establish`、`proof-action`、`proof-final`；插件同步时同时生成仓库自有 proof fixture 与三条 bundled-fixture 质量审批，新工作区完整质量门为 5/5。
